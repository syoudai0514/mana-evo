# 変更後の使い方

## 1. 238体をまとめて端末へ保存できる

保護者・端末設定に **「モンスター画像を全部保存」** を追加します。

対象はNo.001〜238の正式画像だけです。No.239は入りません。

表示は例えば `0/238`、`85/238`、`238/238 保存済み`、`更新あり`、`不足あり` のようになります。

途中で通信が切れても、確認済みの画像は残り、不足分だけ再開します。将来1体だけ画像を差し替えた場合は、その1体だけ更新します。

## 2. 「238/238」を数字だけで信用しない

古い画像が通信成功扱いで返ってきた場合、単に「通信成功」だけを見ると、古い画像なのに238/238と誤判定する危険があります。

そこで画像ごとに登録済みのSHA-256という指紋を使います。

**画像取得 → 実データSHA計算 → 正式SHAと一致確認 → 専用キャッシュへ保存 → 保存成功後だけ完了扱い**

という順番に固定します。

通常閲覧中に不足画像を自動保存する場合も、一括ダウンロードと同じSHA確認処理を必ず通します。昔のキャッシュに同じファイル名があるだけで「現在版」としてコピーすることはしません。

このため、現在版のSHA付きキーが専用キャッシュに存在すること自体を「保存時にSHA確認済み」の証拠として扱えます。

**古い画像・壊れた画像・途中で失敗した画像を「保存済み」と数えません。**

---

# 3. アプリ更新で238枚が消えないように分離する

役割を分けます。

- アプリ本体用: `manaevo-shell-vN`
- モンスター画像保存専用: `manaevo-dex-art-v1`

アプリ本体が更新されても、**画像保存用キャッシュを理由なく全部削除しません。** 同じ画像を2か所へ二重保存する方式にもせず、正式モンスター画像は1つの画像キャッシュが担当します。

---

# 4. 保存済みなら、表示するたび重い確認をしない

保存済み画像を見るたびに、画像一覧の通信取得や238件全走査をすると、せっかく保存してもiPhoneが重くなります。

修正版では通常表示を、**現在版の画像キーを確認 → 端末キャッシュにあれば即表示**を基本にします。

画像一覧の通信取得やキャッシュ全件チェックは、アプリ更新時、「更新する」「不足分を修復」、明示的な保存状態チェックなどにまとめます。

**1枚表示するたびに238件を調べる処理は禁止**です。

---

# 5. 全部保存しても、238枚全部をメモリへ出さない

「端末に画像ファイルを保存すること」と「画像を画面表示用メモリへ展開すること」は別です。238枚を全部一度に展開すると、iPhoneのメモリを圧迫して逆に重くなります。

そのため、ファイルは238体すべて保存可能にしつつ、画面では今見えている画像＋2〜3画面先だけ準備し、詳細では現在のキャラ＋前後2体程度を先読みします。

今の`loading=lazy`だけには任せず、アプリ側でも「今どこまで画像を準備するか」を制御します。

---

# 6. 詳細画面は「前へ／図鑑へ／次へ」

詳細画面に **← まえ　｜　ずかんへ　｜　つぎ →** を置きます。

例えばNo.100を見たあと、そのままNo.101、No.102へ進めます。「ほのお」で絞り込んでいるなら、その検索結果の中だけで前後移動します。一覧の最初・最後では、それぞれ前/次を無効にします。

---

# 7. iPhoneの「戻る」と「ずかんへ」の履歴を正しくする

ここが2回目レビューで残った最後の問題でした。

一覧GからAを開き、次へBへ進んだ場合、履歴は「一覧G → 詳細B」という形になります。

ここで「ずかんへ」を押したとき、**画面だけ一覧へ切り替えてはいけません。** それをすると裏のSafari履歴に詳細Bが残り、あとで別のCを開いてSafariの戻るを押したとき、閉じたはずのBへ戻る可能性があります。

そこで通常の一覧起点では、

**ずかんへ → Safari履歴を1つ戻す → 戻るイベントで一覧を復元**

という順番に固定します。

つまり、

**一覧G → A → 次へB → ずかんへ → 一覧G → C → Safari戻る1回 → 一覧G**

になります。Bへ戻ったら失敗です。

一方、捕獲結果などから直接詳細へ来ていて「直前に図鑑一覧がない」場合は、Safari履歴を勝手に1つ戻すと別画面へ行ってしまう可能性があります。

その場合だけ、現在の詳細履歴を**図鑑一覧の履歴へ置き換えて**から、同じ一覧復元処理を使います。

つまり「図鑑から開いた詳細」と「外部から直接開いた詳細」を明確に区別します。

---

# 8. 一覧へ戻ったとき、元の場所を復元する

保存する情報は、エリア/タイプ絞り込み、検索文字、絞り込みパネル状態、どの検索結果を見ていたか、どのキャラ付近にいたか、そのキャラが画面のどの高さにいたか、です。

戻る時は、**条件を復元 → 一覧を作る → 元のキャラを見つける → 元の画面位置へ合わせる**の順にします。

Safari自身の自動スクロール復元とアプリの復元が競合すると、一瞬上へ飛んでから戻る動きが起きるので、図鑑詳細中はアプリ側がスクロール復元を管理します。

---

# 9. iPhoneで保存データが消える場合も考える

Webアプリの保存領域は、容量不足などでiPhone側から削除される可能性があります。そのため「一度保存したら永久保証」とはしません。

- 1枚だけ消えた → 237/238、不足あり
- 全部消えた → 0/238
- 表示上238でも実物が1枚消えている → 237/238へ訂正
- 表示情報だけ消えていて238枚実物が残っている → 実物を見て238/238へ復元

できるようにします。

容量確認はiPhoneの概算値を参考にはしますが、「空きがあるから絶対保存できる」とは判断しません。実際に保存できなかった場合を最終判定にします。

## 完成したときの理想

一度「モンスター画像を全部保存」する。

図鑑を開く → 画像がすぐ出る → 詳細を開く → 「つぎ」で次々確認 → 「ずかんへ」またはSafari戻る → 元の絞り込み・元の場所へ戻る。

その後また別のキャラを開いてSafari戻るを押しても、さっき閉じた古い詳細へ戻らない。

通信が弱い場所でも238体を確認でき、長く見続けても訪問数に比例してiPhoneがどんどん重くならない。

これを完成条件にします。
