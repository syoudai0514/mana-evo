# 変更後の使い方

## 1. 238体をまとめて端末へ保存できる

保護者・端末設定に

**「モンスター画像を全部保存」**

を追加します。

対象はNo.001〜238の正式画像だけです。No.239は入りません。

表示は例えば、

- 0/238
- 85/238
- 238/238 保存済み
- 更新あり
- 不足あり

のようになります。

途中で通信が切れても、確認済みの画像は残り、不足分だけ再開します。

将来1体だけ画像を差し替えた場合は、その1体だけ更新します。

## 2. 「238/238」を数字だけで信用しない

最初のレビューで一番危なかったのがここです。

古い画像が通信成功扱いで返ってきた場合、単に「HTTP成功」だけを見ていると、**古い画像なのに238/238と誤判定する可能性**がありました。

そこで修正版では、画像ごとに登録済みのSHA-256という指紋を使います。

1. 画像を取得
2. 実際の画像データからSHA-256を計算
3. 正式登録されているSHAと一致するか確認
4. 一致した画像だけ端末キャッシュへ保存
5. 保存成功後だけ1件完了として数える

という順番に固定します。

つまり、**古い画像・壊れた画像・途中で失敗した画像を「保存済み」と数えません。**

また、238という数字だけを別ファイルへ保存して正解扱いにはしません。実際に現在版238個のキャッシュが存在することを基準にします。

---

# 3. アプリ更新で238枚が消えないように分離する

今のアプリにはService Workerという、オフライン表示用のキャッシュ管理があります。

最初の案では、ここに新しい238枚保存機能をどう組み込むかが曖昧でした。

修正版では役割を分けます。

- アプリ本体用: `manaevo-shell-vN`
- モンスター画像保存専用: `manaevo-dex-art-v1`

という考え方です。

アプリ本体が更新されても、**画像保存用キャッシュを理由なく全部削除しません。**

また、同じ画像をService Worker用と図鑑用の2か所へ二重保存する方式にもしていません。

「正式モンスター画像はこの1つの画像キャッシュが担当する」と一本化します。

---

# 4. 保存済みなら、表示するたび重い確認をしない

これも最初のレビューで見つかった問題です。

今のService Workerには、画像を1枚表示するたびに、画像一覧の確認やキャッシュ全件確認を繰り返す可能性がある処理があります。

238体を保存したあとでも、スクロールするたびにそれをやると、せっかく保存したのにiPhoneが重くなります。

修正版では、通常の画像表示時は、

**現在版の画像キーを確認 → 端末キャッシュにあれば即表示**

を基本にします。

画像一覧の通信取得やキャッシュ全件チェックは、

- アプリ更新時
- 「更新する」を押した時
- 「不足分を修復」した時
- 明示的な保存状態チェック時

などにまとめて行います。

**1枚表示するたびに238件を調べる処理は禁止**にします。

---

# 5. 全部保存しても、238枚全部をメモリへ出さない

「端末に画像ファイルを保存すること」と「画像を画面表示用メモリへ展開すること」は別です。

238枚を全部一度に展開すると、iPhoneのメモリを圧迫して逆に重くなります。

そのため、

- ファイルは238体すべて保存可能
- 画面では今見えている画像＋2〜3画面先だけ準備
- 詳細では現在のキャラ＋前後2体程度を先読み

にします。

今の`loading=lazy`だけには任せず、アプリ側でも「今どこまで画像を準備するか」を制御します。

---

# 6. 詳細画面は「前へ／図鑑へ／次へ」

詳細画面に

**← まえ　｜　ずかんへ　｜　つぎ →**

を置きます。

例えばNo.100を見たあと、そのままNo.101、No.102へ進めます。

「ほのお」で絞り込んでいるなら、その「ほのお」の検索結果の中だけで前後移動します。

一覧の最初・最後では、それぞれ前/次を無効にします。

---

# 7. iPhoneの「戻る」も同じ動きにする

今のManaEvo図鑑はReactの画面内状態だけで詳細を切り替えていて、普通のURLページ移動ではありません。

そのため最初の設計では、Safariの戻るボタンをどう扱うかが曖昧でした。

修正版ではHistory APIを使います。

- 一覧 → 詳細を開く: 履歴を1つ追加
- 詳細で「次へ」「前へ」: 同じ履歴を更新するだけ
- Safari/PWAの戻る: 一覧へ戻る

とします。

No.100→101→102と見たあとSafariの戻るを1回押したら、101、100と何回も戻るのではなく、**元の図鑑一覧へ1回で戻ります。**

「ずかんへ」ボタンとSafariの戻るは、同じ復元処理を使います。

---

# 8. 一覧へ戻ったとき、元の場所を復元する

保存する情報は、

- エリア絞り込み
- タイプ絞り込み
- 検索文字
- 絞り込みパネルを開いていたか
- どの検索結果を見ていたか
- どのキャラ付近にいたか
- そのキャラが画面のどの高さにいたか

です。

戻る時は、

**条件を復元 → 一覧を作る → 元のキャラを見つける → 元の画面位置へ合わせる**

の順にします。

Safari自身の自動スクロール復元とアプリの復元が競合すると、一瞬上へ飛んでから戻る動きが起きるので、図鑑詳細中はアプリ側がスクロール復元を管理します。

---

# 9. iPhoneで保存データが消える場合も考える

Webアプリの保存領域は、容量不足などでiPhone側から削除される可能性があります。

そのため「一度保存したら永久保証」とはしません。

代わりに、

- 1枚だけ消えた → 237/238、不足あり
- 全部消えた → 0/238
- 表示上238でも実物が1枚消えている → 237/238へ訂正
- 表示情報だけ消えていて238枚実物が残っている → 実物を見て238/238へ復元

できるようにします。

容量確認はiPhoneの概算値を参考にはしますが、「空きがあるから絶対保存できる」とは判断しません。実際に保存できなかった場合を最終判定にします。

# 10. 今回は238体全部でテストする

最初の案では一部画像や50体程度の長時間テストが中心でした。

「238体全部保存・オフライン」を機能として出す以上、修正版ではrelease前に次を必須にします。

- ネット完全OFFでNo.001〜238全部を表示できる

- 通常図鑑を開いただけで238画像を一斉通信しない

まで確認します。

# 今回レビューで変わったポイント

最初の案から大きく安全になったのは、この4点です。

1. **画像キャッシュの担当を1つに固定した**
2. **238/238はSHA確認済みの実画像だけで判定する**
3. **Safari/PWAの戻る方法を具体的に決めた**
4. **238体全部を使う性能・オフラインテストを必須にした**

なので、今は「よさそうだから実装」ではなく、**この修正版をもう一度別Solにレビューしてもらう段階**です。

再レビューで問題がなければ正式設計書へ昇格し、その後に実装します。
